# Migrating a domain to `camelDb`

Phase 5 of issue #1115. The db layer hand-writes snake_case → camelCase mapping — 887
lines of `camelField: row.snake_field` across 55 modules, 99 `as any` casts propping the
result up, and 57 mapper functions. Kysely's `CamelCasePlugin` does the same job in both
directions for free.

There are two Kysely instances over one pg pool (`connection.ts`):

|           | columns    | types               |
| --------- | ---------- | ------------------- |
| `db`      | snake_case | `schema.d.ts`       |
| `camelDb` | camelCase  | `schema.camel.d.ts` |

Both are generated by `pnpm schema`. Domains move across one at a time, because doing it
in one commit is ~4,900 mechanical edits across the whole backend.

## The recipe

1. **Check the domain qualifies.** See "When a domain does not qualify" below.
2. Swap the import: `db` → `camelDb`.
3. camelCase every identifier string — tables (`'flight.maintenance_note'` →
   `'flight.maintenanceNote'`), columns, joins, `orderBy`, `values({...})` keys.
4. camelCase the row reads in the mappers (`row.created_at` → `row.createdAt`).
5. Replace hand-declared row parameter types with `CamelRow<'schema.table'>` from
   `connection.ts` — `CamelRow<'accts.localFuelPrice'>`, keyed by the same table name the
   query uses. Use this form and not `Selectable<AcctsLocalFuelPrice>`: one idiom across
   the migration, and the table key is checked against the schema. This is also where the
   `as any` casts go — they exist to force hand-mapped rows past types that were written
   by hand in the first place.

   Do **not** keep defensive `String(...)` / `Number(...)` wrappers around a value now
   that it has a real type. `new Date(String(row.createdAt)).toISOString()` is not a
   no-op: `Date#toString()` has no millisecond field, so it truncates the timestamp.

6. **Leave the returned object's keys alone.** They are the API contract, not column
   names, and a few domains deliberately expose snake_case on the wire (`invoicing`,
   `aircraft-pricing` — see `@mik/contracts/invoicing`). Changing them is a breaking API
   change, not a refactor.
7. `pnpm build`, then run the domain's tests.

Steps 3–4 are mostly mechanical and the compiler finds what you miss: with the camelCase
types in place, every stale reference is a `TS2551 … Did you mean 'createdAt'?`.

What does **not** disappear is value coercion — `Number(...)`, `.toISOString()`,
`String(x).substring(0, 10)`. The plugin renames keys; it does not convert types. Mappers
shrink, they rarely vanish.

## When a domain does not qualify

Check all three before starting:

- **It shares a transaction with another module.** A transaction belongs to one Kysely
  instance; `camelDb.transaction()` and `db.transaction()` are different connections and
  do not roll back together. Any module whose functions take a `Transaction<DB>` — today
  `mileage`, `expense-attachment`, `occurrence`, `outbox-simplbooks`, `expense`,
  `inventory`, `meeting` — has to move in the same commit as its callers.
  `maintenance-note` is the smallest example: it opens a transaction and passes it into
  `defect-queries`.
- **It uses raw `sql` fragments.** Identifiers inside a raw fragment are not rewritten
  (they stay valid snake_case SQL), but the _result_ keys are still camelCased by the
  plugin, and nothing typechecks that. Every raw fragment needs reading.
- **It uses `pool.query()` directly**, bypassing Kysely entirely — `ajlb` does. Those
  results are not transformed at all, so the module ends up half-and-half.

## Why `maintainNestedObjectKeys: true` is not optional

`CamelCasePlugin` recurses into arrays and plain objects by default, so it rewrites the
keys _inside_ JSONB values too. This database stores three kinds of JSON that must survive
a read byte-for-byte:

- the `*_audit` tables' `changed_data` / `new_data`, written by triggers as
  `to_jsonb(OLD)` — whole row snapshots keyed by real snake_case column names;
- `outbox.payload`, which is a SimplBooks API request body;
- Emmett's `message_data` / `message_metadata` / `stream_metadata` event-store columns.

Nothing in the backend builds nested objects from columns — there is no `json_agg` or
`jsonb_build_object` anywhere — so no query wants the recursive behaviour, and several are
corrupted by it. `test/db/camel-case-plugin.test.ts` pins this.

## Progress

Migrated: `local-fuel-price`, `aircraft-pricing`, `invoicing`.

Remaining, easiest first — all have db-level tests and no raw SQL:
`cost-centre`, `brevo-sync`, `exam`, `dto`.

Then the ones needing care: `aircraft`, `aircraft-document`, `member`, `occurrence`,
`expense`, `booking`, `tax-report`, `traficom-report`, `flight-log` (raw SQL and/or shared
transactions), and `ajlb` (raw `pool.query`).

When the last one moves, delete `schema.d.ts`, rename `schema.camel.d.ts` over it, and
collapse `camelDb` back into `db`.
