# The data layer

`connection.ts` exports one Kysely instance, `db`, over one `pg` pool. Column names are
camelCase in both directions: you write `noteId`, Postgres receives `note_id`, and rows
come back `noteId` with no hand-written mapper. Types come from `schema.d.ts`, which
`pnpm schema` generates with `kysely-codegen --camel-case`.

That is the whole of it — but the translation between the two spellings has four sharp
edges, all of which have drawn blood in this repo, and none of which `tsc` can see. They
are the rest of this document.

> Until issue #1115 phase 5 finished there were **two** instances: a snake_case `db` and a
> camelCase `camelDb`, so domains could move one at a time instead of in one ~5,000-edit
> change. Both are now the single `db` above. If you find `camelDb` in a comment or an old
> branch, it is this.

## Why `maintainNestedObjectKeys: true` is not optional

`CamelCasePlugin` recurses into arrays and plain objects by default, so it rewrites the
keys _inside_ JSONB values too. This database stores three kinds of JSON that must survive
a read byte-for-byte:

- the `*_audit` tables' `changed_data` / `new_data`, written by triggers as
  `to_jsonb(OLD)` — whole row snapshots keyed by real snake_case column names;
- `outbox.payload`, which is a SimplBooks API request body;
- Emmett's `message_data` / `message_metadata` / `stream_metadata` event-store columns.

Nothing in the backend builds nested objects from columns — there is no `json_agg` or
`jsonb_build_object` anywhere — so no query wants the recursive behaviour, and several are
corrupted by it. `test/db/camel-case-plugin.test.ts` pins this.

## Never rewrite the inside of a raw `sql` template

Raw SQL text is emitted verbatim; the identifier transformer never sees it. Column names
in there must stay snake_case, or Postgres rejects the query outright — `column
r.firstname does not exist`. Only the _result keys_ are camelCased, which is why the
mapper still reads `row.firstName`.

This is easy to get wrong with an automated pass and impossible to catch by eye at scale,
so scan for it before opening a PR:

```
grep -n 'sql`' -A20 src/db/*.ts | grep -E '\b[a-z]+[A-Z][a-zA-Z]*\b'
```

Anything camelCase inside a template is a bug unless it is a `${jsVariable}` or a SQL
comment.

Two ways this has actually shipped:

- `meeting-queries` reached CI green with camelCase inside its SQL because its only two
  raw-SQL functions were **mocked** in the route tests — the SQL never ran. If a module's
  raw queries are not exercised against a real database anywhere, add a db-level test.
- A helper in `stats-my-queries.test.ts` builds its expected value with its own raw query.
  An automated rename turned `AS total_landings` into `AS totalLandings`; Postgres folded
  the unquoted identifier to lowercase, the read came back `undefined`, and `?? 0` turned
  the expectation into `0`. It failed loudly, but only because the assertion compared
  against a real total rather than a literal.

## The camel → snake round trip is not lossless

`schema.d.ts` is generated by converting the real names **to** camelCase. The plugin at
runtime converts your identifiers **back to** snake_case. Those two are not inverses,
because a digit is a word boundary in one direction only:

```
occurrences_per_100h   --codegen-->   occurrencesPer100h   --plugin-->   occurrences_per100h
```

So `db.selectFrom('stats.occurrencesPer100hByAcYr')` **typechecks** — the generated type
says that relation exists — and then fails at runtime with
`relation "stats.occurrences_per100h_by_ac_yr" does not exist`. **The generated types are
not a safe oracle for whether a name is reachable; only executing the query is.**

The whole database has been audited for this: across **174 relations and 1,531 columns,
exactly one relation and one column are affected** — `stats.occurrences_per_100h_by_ac_yr`
and its `occurrences_per_100h` column. If you add a name with a digit immediately after an
underscore, re-run that check.

The fix is the same as for any unreachable identifier: **spell it out in raw SQL.** The
text is untouched, and the result keys are still camelCased on the way out, so the row
type and every caller stay camelCase:

```ts
const { rows } = await sql<{ occurrencesPer100h: number | null }>`
  SELECT * FROM stats.occurrences_per_100h_by_ac_yr WHERE TRUE ...
`.execute(db)
```

`test/db/stats-queries-smoke.test.ts` executes all 43 stats queries against a real
database for exactly this reason.

## `jsonArrayFrom` needs `camelCaseNestedRows`

`jsonArrayFrom` / `jsonObjectFrom` build their JSON inside Postgres from the raw column
names, so the objects _inside_ the array come back snake_case — and
`maintainNestedObjectKeys` tells the plugin to leave nested keys alone. Kysely's inferred
type is derived from the camelCase schema and says otherwise, so the type and the runtime
value disagree with nothing to catch it: `row.updatedAt` is `undefined` and typechecks.

Wrap any nested subquery result in `camelCaseNestedRows` from `connection.ts`.

## Rename identifiers, never data

The single most common way to break a rename, and the compiler catches almost none of it.
Everything below is _data_ that happens to be spelled like a column:

| Form                                                           | Real example                                     |
| -------------------------------------------------------------- | ------------------------------------------------ |
| A sequence name passed to a function                           | `eb.val('accts.credit_note_number_seq')`         |
| An enum value stored in a column                               | `.where('feeType', '=', 'annual_fee')`           |
| A status the code compares against                             | `feeStatus === 'no_record'`                      |
| A sort option from the API                                     | `sort === 'price_asc'`                           |
| An enum member in a contract                                   | `pobBucket: z.enum(['1_2', '3', '4_PLUS'])`      |
| A set of column names compared against **JSONB snapshot keys** | `CHANGE_LOG_IGNORED_COLUMNS` in `member-queries` |

Three of these have shipped as bugs:

- `eb.fn('nextval', [eb.val('accts.credit_note_number_seq')])` — the argument is a
  sequence _name_, not a table reference. Renaming it typechecks perfectly and makes
  `nextval()` fail at runtime. Anything inside `eb.val(...)`, or any string handed to a SQL
  function, is data.
- `CHANGE_LOG_IGNORED_COLUMNS` is a list of column-name strings matched against the keys of
  a `to_jsonb(OLD)` snapshot, which stay snake_case. Camel-casing it silently stopped every
  sync-only update being filtered out of the member changelog.
- `getOutboxItems` takes a filter object whose keys come from `@mik/contracts/outbox` —
  `event_type`, `created_from`. Those are query parameters, not columns. Camel-casing them
  left `filters.event_type` undefined, so every filter silently stopped applying and the
  endpoint returned unfiltered rows. It still compiled, because the type was renamed
  alongside it. Only the route test caught it.

## Some contracts are snake_case on the wire

A db function that validates or returns the _contract's_ shape rather than the row's must
map between the two. These contracts still declare snake_case fields, so a row cannot be
handed to them directly:

`invoicing`, `weather`, `aircraft-pricing`, `outbox`, `prices`, and
`FeeProcessingItemSchema` in `members`.

`member-queries.getFeeProcessingItem` is the worked example — it maps the camelCase row
back before parsing.

By contrast, local `.strict()` row validators like `ShopOrderRowSchema` and
`ShopOrderItemRowSchema` in `simplbooksOutboxHandler` describe _rows_, so they are
camelCase. Being `.strict()`, a mismatch throws rather than misbehaving quietly — which is
how the broken shop-order invoice path was caught.

`stats` used to be the extreme case here, with ~160 snake_case fields returned to the wire
verbatim. It was migrated along with its contract, its query parameters and its frontend,
so `@mik/contracts/stats` is now camelCase throughout.
